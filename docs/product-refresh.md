# 실제 공고 연결과 제품 화면 개편 검증

## 실행한 검사

윈도우 PC의 WSL2 작업 공간에서 아래 검사를 실행했습니다.

- TypeScript 검사와 배포 빌드 정상 완료.
- Vitest 단위 검사 **125개** 통과.
- Node 서버 검사 **8개** 통과.
- Playwright 브라우저 검사 **31개** 통과.

```bash
npm run typecheck
npm test
npm run build
CI=1 JARIZIP_TEST_PORT=4182 npm run test:e2e
npm run test:live
```

일반 브라우저 테스트는 격리된 컨텍스트와 시험용 자료를 사용하며 개인 브라우저 프로필이나 실제 마이크를 사용하지 않습니다. 샘플은 테스트에만 주입하고 새 제품 공간에는 자동 생성하지 않습니다.

## 실제 외부 조회

`test:live`는 원티드 서버를 실제로 호출합니다. Python 검색 결과 **20건**을 받은 실행에서 다음 흐름을 확인했습니다.

검색 → 출처 상세 조회 → 브라우저에 저장 → 지원 준비 공간 생성 → 새로고침 → 지원 당시 공고 원문 유지.

같은 검사에서 데스크톱·모바일 화면과 브라우저 실행 오류를 확인했습니다. 이 결과는 해당 실행 시점의 확인이며, 모든 공고의 접수 가능성이나 출처의 지속 가동을 보증하지 않습니다. 사람인 연결은 실제 발급 키가 없어 실서비스 검증하지 않았습니다.

## 회귀 검사

새 공간에 가상 공고·서류·지원 기록이 없고, 출처 조회 실패 시 오류를 표시하며 예시로 채우지 않는지 확인했습니다. 출처의 내용이 바뀌어도 이전 지원의 원문 스냅샷이 유지되는지 검사했습니다.

검색어 조합, 필터, 추적값이 다른 중복 주소, 공고 수정, 서류 버전 고정, 파일 원본 다운로드, 답변·합성 음성 저장과 재생, 백업 왕복, 잘못된 백업 거부를 검사했습니다. IndexedDB 쓰기를 강제로 실패시켜 저장 성공 안내가 나오지 않고 기존 자료가 남는지도 확인했습니다.

초안 닫기 확인, 계속 작성, 명시적인 버리기, 중첩 창의 스크롤 복원과 키보드 탐색을 검사했습니다. 360px·390px·768px·1024px·1440px 화면 폭, 모바일 검색 이름, 하단 탐색과 알림의 겹침, 지피 말풍선 위치를 확인했습니다.

## 화면과 에셋

지피 캐릭터와 읽기 쉬운 작업 화면을 적용했습니다. 새 공간에 가상 대시보드를 채우지 않고, 실제 공고 탐색과 서류 작성으로 연결합니다.

캐릭터 파일은 앱과 같은 출처에서 제공하며 디코딩 여부를 검사했습니다. 최신 캡처는 `test-results/`와 `.local/live-check/`에 생성되며 Git에는 포함하지 않습니다.

## 한계

원티드 공개 응답은 공식 제휴 API가 아니므로 변경·접근 제한의 영향을 받습니다. 이를 우회하지 않습니다. 미공개 게시일과 급여를 만들어 넣지 않으며, 채용 보상금을 급여로 오인하지 않습니다. 출처의 활성 상태와 수동 확인은 구분합니다.

LLM 생성·평가, 음성 전사, 자동 지원서 전송, 계정 동기화와 공개 운영 인프라는 검증 범위가 아닙니다. 자료 저장은 암호화 보관함이 아니며 브라우저 초기화에 대비한 백업이 필요합니다.
